1. инженерную реализацию и воспроизводимость;

3. системное использование AI с quality control;
4. продуктовое мышление и измеримую пользу;
5. ясную коммуникацию;
6. мотивацию автора.

Твоё демо должно доказывать одну мысль:

> FRAME превращает решения из смет и переписки в проверяемые события с источниками, но финансовое действие подтверждает человек.

## Продуктовый сценарий

Собери связный путь в существующем Vite + React + TypeScript + Tailwind приложении. Не переписывай весь продукт и не трать время на Home Hub, сообщество или каталог подрядчиков.

### Экран 1. AI-контроль проекта

Маршрут `/ai` — старт демо. На первом экране без прокрутки должны быть видны:

- проект «Квартира на Невском»;
- два решения, требующих внимания;
- изменение бюджета `+12 000 ₽` за полную замену старой проводки;
- запрос на приёмку плитки, который ждёт ответа;
- статус режима: `DEMO_FIXTURE`, `LIVE_HYBRID` или `RULES_ONLY`;
- фраза, что ответы основаны только на источниках проекта.

Карточка изменения бюджета должна показывать цепочку источников `#1–#4` и кнопку «Подтвердить доплату». После нажатия:

- состояние меняется на `confirmed`;
- появляется понятный toast;
- в локальном audit log появляется запись;
- сумма не должна «молча» менять бюджет без подтверждения.

### Экран 2. Координатор переписки

Интегрируй AI-карточку непосредственно в `/messages`. Демо-цепочка:

1. Подрядчик: «Проводка старая, полная замена будет +12 000 ₽».
2. Заказчик: «Это если менять полностью, без частичного ремонта?»
3. Подрядчик объясняет риск перегрева/пожара.
4. Заказчик: «Тогда меняем полностью».

Из цепочки должна получиться одна карточка `budget_change`, а не четыре разрозненных события. Карточка показывает:

- тип и состояние;
- сумму;
- краткое объяснение;
- точные source message IDs;
- метод;
- human confirmation.

Добавь ещё 2–3 короткие ветки для демонстрации разных состояний:

- исполнитель завершил плитку и ждёт приёмку;
- задача по розеткам подтверждена исполнителем;
- решение по графитовой затирке уже зафиксировано.

### Экран 3. Объяснимая проверка сметы

Маршрут `/estimates` должен показывать:

- покрытие `13/14`, а не абстрактный AI score;
- 2 369 публичных цен, 22 компании, 7 городов, 47 типов работ;
- медианный ориентир и коридор для сопоставленных работ;

- грунтовка: сигнал на уточнение марки, единицы и состава работ.

Никогда не используй формулировки «справедливая цена», «мошенничество», «доказанная переплата», «подрядчик завысил» или «низкая цена означает плохое качество». Это ориентир для разговора, а не приговор.

### Экран 4. Помощник по проекту

## Честные ML-факты, которые нельзя исказить

### Цена

- На знакомом распределении: линейная модель MAPE 38.7% против 43.6% у медианного baseline.
- При domain shift, LOCO по 22 компаниям: линейная модель MAPE 44.0% против 43.5% у медианы.
- Следствие: production UI использует объяснимый медианный ориентир/коридор, а не предсказание модели.

### Координатор

- Авторский синтетический gold-корпус: 45 сообщений, 19 событий.
- Rules baseline: F1 0.732.
- Hybrid, 3 запуска: precision 0.905, recall 1.000, F1 0.950.
- Linkage: 0.820 ± 0.036.
- State accuracy: 0.895.
- Grounding источников: 1.000.
- Суммы: 4/4.

Подписывай эти числа как валидацию пайплайна на ограниченном авторском сценарии, а не как production accuracy или пользовательский эффект.

## Живая AI-интеграция и режимы

Сделай тонкий service layer и единые TypeScript-типы из `docs/AI_CONTRACTS.md`.

Поддержи:

- `DEMO_FIXTURE` — режим по умолчанию, полностью воспроизводимый и всегда видимый;
- `LIVE_HYBRID` — только если реальный backend действительно использовал и GigaChat Embeddings, и GigaChat extraction;
- `RULES_ONLY` — честный fallback.

Для live-запроса добавь configurable API base URL через Vite env, таймаут и обработку ошибок. Не добавляй ключи, токены и секреты во frontend. Никогда не подменяй упавший live-вызов фикстурой без видимой смены режима.

В backend добавь минимальный стабильный HTTP API поверх уже существующего `analyze_hybrid`, не переписывая ML-пайплайн. Предпочтительные контракты:

- `GET /api/health`
- `POST /api/coordinator/analyze`
- `POST /api/estimate/analyze`

Ответ координатора обязан содержать:

- события и `source_message_ids`;
- фактический mode;
- `retrieval_backend`: `gigachat_embeddings`, `local_embeddings` или `rules`;
- `extraction_backend`: `gigachat` или `rules`;
- validation errors/warnings;
- elapsed time без утечки внутренних секретов.

Используй существующие backend-переменные из `.env.example`, включая `LLM_AUTH_KEY`, `LLM_SCOPE`, `GIGACHAT_EMBEDDINGS_API_BASE` и `GIGACHAT_CHAT_API_BASE`. Ключ находится только в backend `.env`. Не печатай его в terminal output, браузер, лог, exception или итоговый отчёт.

Критически важно: для retrieval вызывай именно `src/gigachat_embeddings.py` и embeddings endpoint. Не заменяй это chat completion и не называй chat-модель «эмбеддингами». Если embeddings недоступны, покажи реальный fallback mode.

Добавь CORS только для локального frontend origin. Сохрани существующий Gradio demo, если он не мешает.

Создай безопасный demo launcher для Windows, например `start-demo.ps1`, который:

1. запускает backend;
2. ждёт успешный `/api/health`;
3. запускает frontend;
4. выводит только адреса и режим, но не секреты.

Если live-вызов невозможно подтвердить из-за отсутствия ключа или сети, не блокируй демо: оставь рабочий `DEMO_FIXTURE`, точную диагностику и одну команду, которой пользователь проверит live-режим после добавления `.env`. Не симулируй сетевой вызов.
