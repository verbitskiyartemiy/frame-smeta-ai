# FRAME · AI-слой управления ремонтом

[![tests](https://github.com/verbitskiyartemiy/frame-smeta-ai/actions/workflows/tests.yml/badge.svg)](https://github.com/verbitskiyartemiy/frame-smeta-ai/actions/workflows/tests.yml)

FRAME превращает неструктурированную переписку о ремонте в проверяемые события:
решения, изменения бюджета, сроки, вопросы и приёмки. Встроенный помощник отвечает
по фактам проекта и найденным фрагментам базы знаний, показывает источники и может
предложить напоминание. Никакое действие не выполняется без подтверждения человека.

Это конкурсный R&D-прототип, а не заявленная производственная точность.

## Что показать за 90 секунд

1. Открыть `/messages` и запустить разбор диалога про замену проводки.
2. Показать карточку «Доплата 12 000 ₽» и исходные сообщения, из которых она собрана.
3. Подтвердить карточку человеком — только после этого она попадает в журнал проекта.
4. Открыть `/ai`, спросить: «Что проверить перед приёмкой электрики?»
5. Показать ответ, точные источники и предложенное действие «Создать напоминание».

Главный продуктовый эффект: значимое изменение фиксируется до того, как повлияет на
бюджет или срок, а пользователь может проверить, откуда система взяла вывод.

## Архитектура

```text
чат / смета / данные проекта
          │
          ▼
правила с высоким recall ──► кандидаты событий
          │
          ▼
GigaChat Embeddings ───────► связь разнесённых реплик и поиск знаний
          │
          ▼
LLM со строгой JSON-схемой ► тип события, статус, краткая формулировка
          │
          ▼
валидатор источников и чисел
          │
          ▼
карточка-предложение ──────► подтверждение человеком ─► действие
```

Правила хорошо находят явные суммы и даты. Embeddings связывают реплики по смыслу.
LLM нормализует контекст в структуру. Детерминированный валидатор не пропускает
несуществующие сообщения, суммы и ссылки. Такое разделение позволяет использовать
сильные стороны моделей, не отдавая им право менять проект.

## Состояние функций

| Функция | Статус | Что реально работает |
|---|---|---|
| Координатор переписки | **демо готово** | правила + GigaChat Embeddings + LLM + валидация + подтверждение человеком |
| Помощник по ремонту | **демо готово** | факты проекта + поиск по базе знаний + цитаты + предложение действия |
| Проверка сметы | **простая продуктовая функция** | арифметика, дубли, медиана и P10–P90; не «детектор завышений» |
| Аспектный рейтинг подрядчиков | **R&D остановлен** | эксперимент не прошёл заранее заданный порог качества |

## Результаты и честные границы

### 1. Координатор переписки

На небольшом авторском синтетическом наборе из 45 сообщений и 19 вручную
размеченных событий три живых прогона дали:

| Метрика уровня события | Правила | Гибрид |
|---|---:|---:|
| F1 обнаружения события | 0.732 | **0.950 ± 0.000** |
| Точная связь нескольких реплик | 0.000 | **0.820 ± 0.036** |
| Статус события | 0.333 | **0.895 ± 0.000** |
| События с существующим источником | 1.000 | **1.000** |

Источник: [`reports/hybrid_coordinator_stability.json`](reports/hybrid_coordinator_stability.json).

Чтобы не ограничиваться одним написанным вручную диалогом, проведён дополнительный
стресс-тест на 50 сгенерированных диалогах: 326 сообщений и 32 события двух
размеченных типов. На нём гибрид дал F1 **0.800**, правила — **0.545**; grounding
источников — **1.000**. В 18 «тихих» диалогах гибрид создал 5 лишних карточек,
поэтому до пилота нужен отдельный порог по `false-card rate`.

Источник: [`reports/corpus_eval.json`](reports/corpus_eval.json).

Ограничения:

- оба корпуса синтетические и не доказывают точность на реальных чатах;
- расширенный корпус сгенерирован моделью, близкой к модели извлечения;
- разметка связи реплик и статуса в расширенном корпусе оказалась ненадёжной,
  поэтому эти две метрики на нём не заявляются;
- следующий quality gate — обезличенные реальные чаты, независимая двойная
  разметка и отдельный holdout.

### 2. Помощник по проекту и ремонту

Помощник использует два разных контекста:

- **факты проекта** — смета, журнал решений, события из переписки;
- **знания о ремонте** — найденные фрагменты по этапу работ.

В ответе backend требует идентификаторы использованных фактов и знаний. Он удаляет
неизвестные ссылки и блокирует ответ, если LLM добавила число, которого нет в
процитированных источниках. База знаний в репозитории имеет статус
`demo_checklist_unverified`: до пилота её должны проверить профильные эксперты и
нормативные источники.

Помощник не создаёт задачу сам: `proposed_action` имеет статус `pending`, а действие
появляется в журнале только после клика пользователя.

### 3. Что показал эксперимент со сметами

Собрано 2 369 публичных цен 22 компаний из 7 городов, нормализованных к 47 типам
работ. На случайной кросс-валидации линейная модель выглядела лучше медианы:
MAPE 38.7% против 43.6%. Строгая проверка leave-one-company-out показала другое:
на новой компании модель получила MAPE **44.0%**, медиана по виду работы —
**43.5%**; модель выиграла только на 12 компаниях из 22.

Вывод: признак источника частично позволял запоминать ценовой уровень компании.
Усложнение модели не решает отсутствие контекста объекта. Поэтому в продукт
выпущены только:

- точная арифметическая проверка и поиск дублей;
- объяснимый медианный ориентир и диапазон P10–P90;
- отказ от оценки неизвестной позиции.

Модель цены и формулировка «детектор завышений» в продукт не выпущены.

Воспроизводимые результаты:

- [`reports/baseline_ladder.json`](reports/baseline_ladder.json);
- [`reports/data_ceiling.json`](reports/data_ceiling.json);
- [`reports/metrics.json`](reports/metrics.json);
- [`src/eval_baseline_ladder.py`](src/eval_baseline_ladder.py).

### 4. Остановленный эксперимент с рейтингом

На 1 212 отзывах проверялось выделение аспектов и тональности. На ручном gold set
из 108 примеров точность аспекта составила 0.513. Для трёхклассовой тональности
нейросеть дала 0.630, но majority baseline — 0.824 из-за дисбаланса; recall
негативного класса равен 0. Функция не прошла quality gate и оставлена в R&D.

Источник: [`reports/absa_gold_metrics.json`](reports/absa_gold_metrics.json).

## Как проводился Data Science

1. **Сформулирована продуктовая ошибка**, которую нужно предотвращать, и единица
   оценки: событие, а не отдельное сообщение.
2. **Собраны и очищены данные**; зафиксированы происхождение, объём и ограничения.
3. **Проведён EDA**: распределения цен, разрыв между компаниями, покрытие работ,
   дисбаланс отзывов.
4. **Построены простые baseline** до сложных моделей: правила, медиана, majority
   class.
5. **Проверены альтернативы**: линейная регрессия и XGBoost; правила, embeddings и
   гибрид; словарная и нейросетевая тональность.
6. **Проверен перенос на новые данные**: обычный CV дополнен LOCO по 22 компаниям.
7. **Проведён анализ ошибок и потолка данных**. Он показал, где мешает модель, а
   где — отсутствие признаков или плохая разметка.
8. **Принято продуктовое решение через gate**: выпустить, упростить или остановить.
9. **Эксперименты сохранены** в JSON/Markdown-отчётах; код, данные и тесты лежат в
   репозитории.

Этот процесс привёл не к максимальному числу ML-функций, а к трём разным решениям:
гибрид выпустить в демо, смету упростить, аспектный рейтинг остановить.

## Как именно применялся ИИ при разработке

ИИ использовался системно как рабочий инструмент, а не как источник непроверенных
утверждений.

| Этап | Что делегировалось ИИ | Контроль человека | Полученный эффект |
|---|---|---|---|
| Исследование задачи | разбор требований конкурса, гипотезы, карта рисков | выбор проблемы и продукта, проверка формулировок | быстрее отсеяны слабые сценарии |
| Data Science | генерация вариантов признаков, кода EDA и экспериментов, анализ ошибок | запуск на данных, проверка leakage, LOCO и baseline | обнаружен ложный выигрыш модели цены |
| Разработка | каркас API, тесты, типы, интерфейс, документация | code review, локальные тесты, сборка, Git | backend и frontend собраны в воспроизводимое демо |
| Работа с данными | синтетические сценарии для проверки пайплайна | происхождение явно маркируется; реальные метрики не приписываются | появилась ранняя проверка до сбора живых чатов |
| Коммуникация | варианты сценария демо и слайдов | финальные claims сверены с JSON-отчётами | технический результат переведён в продуктовый вывод |

Использованные инструменты:

- **Claude / Claude Code и Codex** — исследование, программирование, ревью,
  тестирование, документация и подготовка демо;
- **GigaChat API** — LLM-извлечение структуры событий и ответы помощника;
- **GigaChat Embeddings API** — смысловая связь реплик и поиск фрагментов знаний.

Правила контроля:

- результат ИИ не считается доказательством без воспроизводимой проверки;
- синтетические данные всегда помечаются;
- метрики читаются из сохранённых отчётов, а не придумываются для слайда;
- код проходит тесты и сборку;
- внешнее действие требует подтверждения человека;
- при недоступности модели координатор явно переходит в `RULES_ONLY`, не выдавая
  заготовку за живой AI.

Главный эффект ИИ в разработке — скорость итераций: стало возможно проверить
несколько гипотез и собрать end-to-end прототип одному автору. Главный человеческий
вклад — постановка задачи, выбор метрик, отбраковка неверных выводов и решение,
какую функцию действительно выпускать.

## Локальный запуск полного демо

Требования: Python 3.11/3.12 и Node.js 22.

```bash
git clone https://github.com/verbitskiyartemiy/frame-smeta-ai.git
cd frame-smeta-ai

python -m venv .venv
# Windows:
.venv\Scripts\activate
pip install -r requirements-app.txt
copy .env.example .env

python src/demo_api.py
```

Во втором терминале:

```bash
cd frontend
npm ci
npm run dev
```

Открыть `http://127.0.0.1:5174/ai`. Backend health:
`http://127.0.0.1:8000/api/health`.

Для живого режима заполнить в локальном `.env`:

```dotenv
LLM_PROVIDER=gigachat
LLM_AUTH_KEY=
LLM_MODEL=GigaChat
GIGACHAT_EMBEDDINGS_API_BASE=https://api.giga.chat/v1
```

`.env` исключён из Git. Без ключа координатор работает в явно обозначенном
`RULES_ONLY`; помощник честно сообщает, что сервис недоступен.

### Лёгкое Gradio-демо в Docker

```bash
docker build -t frame-ai .
docker run --rm -p 7860:7860 frame-ai
```

Docker-образ запускает исследовательское Gradio-демо. Конкурсный интерфейс находится
в `frontend/` и запускается отдельно, как описано выше.

## Проверки

```bash
pip install -r requirements-ci.txt
pytest tests/ -q
python -m compileall src

cd frontend
npm ci
npm run lint
npm run build
```

GitHub Actions выполняет Python-тесты на 3.11 и 3.12, lint и production build
React-интерфейса. Тесты не обращаются к внешним API: модель и сеть подменяются
заглушками.

## Следующий quality gate

1. Получить обезличенные реальные чаты с согласиями участников.
2. Разметить события двумя независимыми аннотаторами и измерить согласие.
3. Зафиксировать отдельный holdout по проектам и подрядчикам.
4. Измерять event precision/recall, точность связи реплик, `false-card rate`,
   время до подтверждения и долю исправленных карточек.
5. Для помощника заменить демонстрационные знания на проверенные документы с
   версиями и владельцем источника.
6. Выпускать функцию только после прохождения заранее заданного gate; при
   деградации — откат к правилам или отказу от ответа.

После накопления собственных данных FRAME сможет сравнивать несколько предложений
на один и тот же объект, прогнозировать риск роста бюджета по подтверждённым
доплатам и находить вероятно пропущенные позиции сметы. Именно контекст проекта,
а не ещё одна более сложная модель на публичных прайсах, снимает обнаруженное
ограничение данных.
